# Execution notifications and sticky removal (#8)

The extension stores an atomic per-Run `deliveries.json` outbox independently of execution snapshots. Each event has Run/attempt execution identity, owner session identity, and a stable event ID. Completion, failure and safe pause carry a 3,000-character answer/handoff excerpt and a `subagent_status` full-retrieval pointer. Structured failed/uncertain tools produce concrete blocker attention; unchanged activity and tool count for two minutes produce deduplicated stall attention. Ordinary progress never becomes a parent message.

Busy parent work keeps these events durable and queued. An idle parent or `agent_settled` boundary inserts context-only custom messages without starting reasoning or steering active work. Receipt means an actual retained host entry (or an actual extension `message_end` if the host emits one), never `sendMessage` queue acceptance. Reload reconciles existing entries before resending, including insertion-before-receipt crash windows. Successful and failed sticky rows leave only after receipt; safely Paused work remains visible. Historical delivered rows stay absent after reload.

Installed SDK observation: idle `sendCustomMessage` synchronously appends a `custom_message` session entry and emits `message_end` to host subscribers. It does not route that event through extension handlers. Consequently retention reconciliation is the operative receipt in this installed version. Neither queue acceptance nor subscription assumptions falsely acknowledge delivery.

Provider spend in notification details is informational; the SDK does not add custom-message usage to its standard usage totals. The first management retrieval (status/wait/cancel) reports the outstanding delta through the supported tool-result `usage` field; subsequent retrievals report none. Previously reported tool results also suppress notification's informational delta. Recovery retains cumulative spend with a new execution-attempt identity; cumulative accounting baselines never decrease. There is no public ordinary extension-context API for automatically appending standalone standard SDK usage entries, so SDK totals update on management retrieval rather than notification insertion.
