# Retained conversation follow-up acceptance (#10)

`subagent_followup({run, task, reuse?, fresh?, nonblocking?})` assigns a new task to an idle successful child. Each parent tool-call identity produces its own execution ID. `Run.conversationId` identifies the retained SDK database, defaulting to the original execution ID for historical records; `previousExecutionId` records the originating result. Metadata, answers, usage, and notification outboxes stay execution-scoped. The new seed explicitly lists its authority fields, so historical group membership and old progress cannot leak into the new execution.

The Agent, model, thinking, tools, and workspace stay fixed. Additional authority fields are rejected, and tools unavailable to the original child remain unavailable even if the host now exposes them. Persisted delegation depth preserves bounded nested delegation. Provider request session affinity follows conversation identity across retained execution and compaction; fresh conversations receive new identity. No old tool effects or submissions are replayed. Original tool counts/results remain under their original execution.

Admission reacquires the shared conversation lease, workspace ownership, and per-parent active capacity. Busy work rejects new tasks; guidance uses `subagent_steer`, unfinished work uses explicit continuation/recovery. Repeated accepted follow-up calls retrieve their execution handle. A context warning includes measured context health and requires `reuse:true`; `fresh:true` creates a fresh conversation with the same authority. Unknown capacity remains unknown. Inspection of an earlier execution during active follow-up returns its historical answer and reads the current conversation through the active public projection.

The admission-time SDK cumulative usage ledger becomes `Run.usageBaseline`. Execution usage subtracts that baseline, including all earlier execution and separately billed compaction spend, then subtracts separately billed compaction operations belonging to the current execution. Retrieval accounting recognizes the new host tool and omits detached-start spend until a control result reports it. Provider-boundary usage receipts verify that a follow-up reports exactly its own generation usage, including cache fields, rather than all conversation history.
